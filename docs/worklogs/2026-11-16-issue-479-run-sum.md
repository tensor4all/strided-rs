# 2026-11-16: #479 Part 1 — the sorted-run reduction

Issue: [tensor4all/strided-rs#479](https://github.com/tensor4all/strided-rs/issues/479).
Scope: Part 1 only, the typed sorted-run reduction in `strided-basic`
(`RunIndex`, `RunSumPlan`) plus the two error variants it needs in
`strided-view`. Part 2 (the segmented-polynomial executor) and the
dtype-erased replay in `strided-kernel` are **not** in this change; the
maintainer's pre-implementation review on the issue said Part 1 is ready and
Part 2 needs D1–D11 first.

## 1. What the kernel does and why it exists

`ScatterPlan` handles `dest[e] += src[r]` for a message-passing loop, but its
additive scatter is a read-modify-write per edge: not deterministic under a
budget, and one atomic or one serial pass. A CSR topology already knows which
edges belong to which node, so the accumulation can be a *reduction* per
destination row instead:

```text
dest[r, ..] (=|+=) Σ_{j in ptr[r]..ptr[r+1]} src[perm[j], ..]
```

Each run is summed by exactly one worker, in increasing `j`, and `compile`
requires an injective destination layout, so rows are disjoint between runs. No
atomics, no partial sums, no budget-dependent bits.

## 2. The two halves of topology time

`RunIndex::from_dest(dest, num_runs)` does a stable counting sort: one pass for
the counts, prefix sums for the offsets, and — only when the list is not
already non-decreasing — a placement pass that fills `perm`. A list that is
already grouped keeps `perm = None`, so the replay indexes rows directly.
`RunIndex::from_ptr(ptr)` takes offsets a caller already grouped and holds them
as given.

This is the allocation boundary: sorting, `compile` and the fused payload
traversal allocate once, and `execute_into` / `execute_acc` allocate nothing.
The zero-allocation counter in `strided-basic/tests/run_sum_alloc.rs` holds that
line for payload rank 0..=8, serially and on a two-thread pool.

## 3. Replay

The payload walk is the existing `for_each_inner_block_with_offsets` over the
fused payload axes with two operands (`[dest, src]` strides), so block shape and
fusion are the kernel machinery's, not a second traversal. Each block is a
`zero_block` (for `execute_into`) plus one `add_block` per row of the run.
Splitting happens only between runs, at the row-count midpoint, and only while
the token has budget left — hence the budget independence above.

The width comes from `cost::tree_width`, not `parallel_width(elements, 1)`: the
dispatch is a tree of forks, so the region pays `log2(k)` sequential dispatches on
a path, which is exactly what `tree_width` prices. The estimate counts both the
source rows and the destination writes, because `execute_into` writes every
destination row even when the source has none.

A plan with runs but no source rows does not walk the source at all. An empty
source's payload strides carry no bound — `RawStridedRef` validates the reach of
the whole layout, and a zero row extent makes it empty — so walking them lets the
odometer overflow on strides the constructor accepted (`isize::MAX` does it).
`execute_acc` returns; `execute_into` zeroes the destination rows by walking the
destination alone.

## 4. Deliberate non-changes

- **Not blocked, not SIMD-dispatched.** A run is a chain of dependent adds, so a
  blocked/SIMD form needs a reformulation the executor work owns. One long run
  is one worker's work; the topology amortizes it only if the runs are numerous.
- **`StridedError` stays without `#[non_exhaustive]`.** The two new variants
  (`InvalidRunIndex`, `IndexOutOfRange`) therefore break a downstream exhaustive
  match, which is why they land in the unreleased 0.15.0 minor. Adding the
  attribute is itself breaking and is the maintainer's call.
- **No erased replay.** The dtype-erased side is the completing half named above,
  not a silent omission.
- **`perm: Option<Vec<usize>>` stays.** The identity shortcut is what makes an
  already-grouped list free; the alternative (always materialising `perm`) would
  allocate on the common path.

Four things that check found, all worth recording:

- **Real UB, found by miri and fixed.** `zero_block` / `add_block` advanced a
  pointer by the inner stride *after* the last element, forming an
  out-of-bounds pointer even though it was never dereferenced. Native runs pass
  silently; miri reports `in-bounds pointer arithmetic failed`. Both loops now
  compute each address from the base (`base.offset(k * inner)`), so no pointer
  past the final slot is ever formed.
- **An empty source could overflow the walk (post-review, fixed).** See §3's
  last paragraph. The regression is
  `tests::empty_source_rows_zero_the_destination_without_walking_it`; before the
  fix it panics in `kernel.rs:487` with `attempt to add with overflow`.
- **An impossible run count panicked instead of erroring (post-review, fixed).**
  `RunIndex::from_dest(&[], usize::MAX)` allocated one `usize` per run, so the
  allocation panicked with `capacity overflow` before any index was validated.
  The run count is now bounded before the allocation and returns
  `StridedError::OffsetOverflow`; `tests::from_dest_rejects_a_run_count_it_cannot_allocate`
  fails with that panic before the fix.
- **The parallel tests are not compiled under miri.**
  `threading::test_pool` reads the host topology through the filesystem, which
  miri's isolation refuses, so the module is `#[cfg(all(test, not(miri)))]`. The
  serial property tests are the miri surface for the module.

Mutation check (reverted, not part of the diff): reversing the row order inside
a leaf fails `property_matches_scalar_reference`,
`property_holds_for_f32_and_complex` and `degree_skew_balances_by_rows`, so the
scalar oracle is order-sensitive. `regrouping_a_run_would_move_the_bits` keeps
the bit-for-bit budget test from being vacuous: the hub run's rows provably do
not sum to the same bits when regrouped. A budget-*dependent* mutant was not
constructed; that class is covered by the no-shared-slot design plus the
increasing-`j` order, both of which the topology tests exercise.

### Post-implementation review

A second, independent review of the finished diff ran on `openai/gpt-6.1-sol`
(read-only, findings first): **`VERDICT: CHANGES`**, six important and three
minor.

Fixed:

- Empty sources traversed unvalidated source strides → §3.
- `from_dest` panicking on an unallocatable run count → §5.
- The width came from `parallel_width(.., 1)` while the dispatch is a tree of
  forks → `tree_width`; the estimate ignored destination writes → counts both.
- The property-test layouts were gapped by construction (`next += dim * stride`
  left a one-element hole), so payload fusion was never exercised → contiguous
  packing plus explicit gaps.
- The anti-vacuity check used different data from the payload it claimed to
  describe, and the cross-budget bit comparison covered only `f64` → both now
  derive from `Sample::from_index` and run on `f32`/`f64`/`Complex64`.
- The `Outcome` struct was deleted (its only reader wanted a count).

Documented rather than changed:

- A fused payload of more than eight axes allocates in
  `kernel_nd_inner_iterative` (`kernel.rs:560`). The rustdoc, CHANGELOG and this
  worklog now say so instead of "allocate nothing" unconditionally; removing that
  `Vec` is `strided-kernel`'s traversal, not this plan's.
- Adding variants to `StridedError` breaks exhaustive downstream matches, and
  `strided-view` is still unpublished at 0.8.1. The release shape is the
  maintainer's decision; the CHANGELOG says so.
